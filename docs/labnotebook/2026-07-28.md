**Index:** `plot_pain_view_heatmaps.py` calls `log_analysis()`.

**Saw:**

- **Epochs are NOT one Parquet row group each, and assuming so would have been
  invisible.** `ParquetWriter` splits a `write_table` above ~1,048,576 rows, and an
  epoch is `n_windows x n_pairs x n_bins` — so a 300-window subject crosses the
  ceiling at 70 pairs. sub-019 (35 pairs, 525k rows) is 1:1; sub-039 (85 pairs,
  1.275M rows) is 2 row groups for 1 epoch. A 1:1 assumption would have read the
  wrong slice for most of the cohort and still produced a plausible heatmap. Epochs
  now map to contiguous row-group RANGES, checked by exact cumulative row-count
  alignment. The guard that caught this was written before the data was read.
- **A per-run baseline strands epochs.** First implementation keyed the baseline on
  `(run, pair_index)`; sub-019 has 26 runs and several carry no 0-pain event, so 4
  of 49 epochs got no baseline. Registry AXIS 2 says "the subject's 0-pain epoch
  windows", so the baseline is now session-wide and keyed on channel NAME, with each
  run's pair axis mapped onto a shared index (montages can differ between runs).
- **The extreme heatmap cells are line noise.** The group z-score figure had one
  S2 (supramarginal) cell at +5.2 flattening the shared colour scale. It resolves to
  sub-090 only (2 channels, 4 low epochs) at freq bins 37/46/47/48/49 — and the unit
  manifest flags 36/37/43/46/47/49 as `contains_line_noise`. 60/120/180/240 Hz
  harmonics, not signal. `|value|` p50 0.065, p99 1.02, p100 5.16. Re-ran with
  `--drop-line-noise-bins`. NOMINATION only; no threshold was tuned to make the
  figure look better.
- **4 of 83 subject-sessions have NO `Desikan_Killiany_anode` column at all** —
  `093, 154, 159, 240` — so they cannot enter a region-level view under any ROI
  scheme, and their view table comes out empty. sub-159 was in the random sample,
  which is the only reason this surfaced now rather than mid-sweep.
- **P0.6's underflow hazard does not materialise in float64.** sub-088 (stored
  minimum log-power −36.8) through the `linear` domain: 12250 values, **0 exact
  zeros**, min |value| 8.9e-20, all finite.
- **The self-baseline identity holds to machine epsilon.** An epoch normalized

## 12:55 — Addendum: the timing audit found stale 60s-hop PSD in two subjects

The `epoch_start_sec`/`hop_sec` backfill (array `36197924`, 83 tasks, 2937 runs)
completed. 81 of 83 subject-sessions are uniformly `starting_time=0.0, rate=1.0`.
**Two are not**, and this is the finding that justifies auditing rather than
assuming:

| | 1 s hop | 60 s hop |
|---|---|---|
| sub-247 | 39 epochs, 300 windows, 33 runs | **19 epochs, 5 windows, 13 runs** |
| sub-257 | 37 epochs, 300 windows, 25 runs | **14 epochs, 5 windows, 11 runs** |

`rate = 1/60`, i.e. these runs' `psd_log_bins` were written under the **old 60s
outer-window design** that `config/psd_params.py` documents as superseded by the
current 2 s window / 50% overlap scheme. Both sessions MIX the two: within one
subject, some epochs average 300 windows and others average 5, and nothing
downstream distinguished them.

Two consequences:

1. **The mask join would have been silently wrong by 60x** for those 24 runs if
   `hop_sec` had been hardcoded to 1.0 — which was the shortcut on the table. The
   derived columns are computed per run, so masking is correct for them as built.
2. **A 5-window epoch mean is not the same feature as a 300-window epoch mean.**
   Pooling them into one `pain_bin` average mixes two feature definitions, and the
   5-window epochs have ~sqrt(60) more noise per estimate. These 33 epochs should
   not enter a sweep until the PSD is re-run for those runs under the current
   scheme, or they are excluded explicitly.

Not fixed here: this is upstream of the view layer (BG.1 territory), and choosing
between re-running the PSD and excluding the epochs is a cohort decision, not a
plumbing one.
